## 选 Qwen的小模型作为训练对象，用 Unsloth + LoRA 微调
**下面用qwen3.5-9B模型演示流程,因为最后有多个版本**

![角色模型训练与部署流程图](/img/posts/glowspire-model-flow.png)

**效果:** 模型体量小,数据干净,满足聊天模型的需求
	1. 本地部署本地跑,无费用消耗
	2. 模型体量小,性能要求低,回复速度快
	3. 数据干净,角色扮演效果好

**云端模型训练(基座模型 + 持续喂数据微调)**
- 配置环境: 选用阿里云端开发环境/魔塔社区一条龙部署(优先)
- 数据来源: 选用游戏原对话作为"种子对话",调用其他大模型进行扩写
- 定向扩展: 对扩写内容进行润色,筛选,添加偏向预期性格的内容

最初计划采用QLoRA,通过4bit加载基座来降低训练显存占用.但在调查后,发现Unsloth 官方文档明确写"不建议对 Qwen3.5 系列做 QLoRA(4-bit)训练,无论 MoE 还是稠密",原因是它的量化敏感度高于往常,BitsandBytes 有兼容限制,因此改用了BF16基座上的LoRA微调.
同时,**4-bit 训练和训练完成后的 GGUF 量化是不同环节**.前者的限制不代表后者一定不能使用,所以我选择了在本地推理的时候进行4-bit量化后本地部署.

### Unsloth + LoRA 微调
### **第一步：数据准备**

训练数据以游戏原始对话作为种子，结合其他大模型扩写，再进行人工筛选、润色、去重与合并。
实际对话种子质量比较差，大部分重复，句子过短，必须经过人工审核修改，最主要的是训练出自己喜欢的人格，这要求你凭空造句和人为捏造一些场景来填补原数据的空缺，直接让 LLM 模型进行扩写质量参差不齐，但同时能做为参考数据，**这一步我认为是训练最关键的一步**，能直接决定你的最终的模型质量。

数据整理重点包括：

1. **稳定的人设:** 明确角色的身份、经历、性格、表达习惯，以及与用户的关系。
2. **自然的表达:** 保留角色语气，避免每次回复都重复口头禅、安慰句或固定动作。
3. **多样的场景:** 覆盖日常闲聊、情绪回应、意见分歧、追问和多轮对话，而不只训练一种互动方式。
4. **一致的标记:** 情绪、动作和语气标记按照统一约定使用，方便应用解析和驱动立绘、TTS。

数据可以使用ShareGPT风格保存为JSONL，例如一条数据为：

```json
{"conversations":[{"from":"system","value":"角色人设与回复格式要求"},{"from":"human","value":"今天好累啊"},
{"from":"gpt","value":"[emotion:难过]辛苦啦。（轻轻靠近）要不要先休息一会儿？"}]}
```

ShareGPT是数据组织方式，模型实际接收的输入仍需要通过对应的聊天模板构造。训练与部署时，应保持角色设定、角色顺序和特殊标记的使用一致，例如人设一定要使用相同的一套，不然效果会变差，模型不是在根据训练的数据回答，而是在思考模仿人设卡。

### **第二步：在云端以BF16加载基座模型**

实际训练使用云端24GB显存的GPU。基座模型以BF16精度加载，不启用4bit量化。

```python
import torch
from unsloth import FastLanguageModel
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen3.5-4B",   # 云上24G档；本地8G卡换成 Qwen3.5-4B
    dtype=torch.bfloat16,
	load_in_4bit=False,            
)
```

**云端训练使用的模型，与后面合并、量化时使用的基座必须对应。本地显存约束通过部署阶段的量化与推理配置处理。**

### **第三步：挂 LoRA 适配器**

加载基座后，使用LoRA向指定模块添加可训练的低秩矩阵。训练过程中，基座权重保持冻结，只优化LoRA参数。
需要记录的主要配置包括：

- `r`：LoRA的秩，影响适配器容量与可训练参数量。
- `lora_alpha`：适配器更新的缩放参数。
- `lora_dropout`：适配器分支的dropout设置。
- `target_modules`：实际挂载LoRA的模块。
- 是否启用梯度检查点等显存优化。

这些参数应填写最终训练脚本中的实际值。

LoRA减少了需要计算梯度和保存优化器状态的参数量，但**BF16基座权重、训练激活和其他运行开销仍然占用显存**。因此，不能根据“只训练少量参数”就推导出“8GB显存也能完成同样的BF16训练”。

### **第四步：训练超参数**

学习率 5e-5 起步，epoch 先设 1（角色微调经常一轮就够，多轮极易过拟合成人设复读机），batch size 2 + 梯度累积 4，优化器用 adamw_8bit 省显存，训练时监控 loss。这里有个反直觉的点：**loss 越低不代表模型越好**，训练 loss 在降而验证集 loss 在升，就是模型在背你的数据集，跟"她"聊新话题就会崩。我记录中的极差最大的比最小大了3倍之高

### **第五步：中途验证效果**

训练完先不合并，用验证集那 10-15% 的样本让模型生成回复，跟基座模型对照。检查三件事：回复是否遵循人设、语气是否一致、有没有复读训练数据原文。如果微调后跟基座输出几乎没差别，说明适配器没生效（检查有没有加载对 checkpoint）。

### **第六步：合并与导出**

具体顺序为：

```text
BF16基座＋训练完成的LoRA适配器
                ↓
          合并完整模型权重
                ↓
          转换为GGUF格式
                ↓
         进行4bit部署量化
                ↓
     本地8GB显存设备加载推理
```

LoRA 适配器本身不能独立部署，要合并回基座：model.save_pretrained_merged() 得到完整权重，再用 llama.cpp 的 convert_hf_to_gguf.py 导出 GGUF 格式，量化选 Q5_K_M（8B 模型约 4.6GB）。然后写个 Ollama Modelfile 就能本地加载了。

### **第七步：部署聊天 + 收集问题 + 迭代循环**

这一步必须强调：**训练和推理时的 prompt 模板要完全一致**。在训练数据里 system 字段写了人设卡，推理时就必须同样把人设卡放进 system 位置，格式错一点，模型的表现就掉一档。部署后进入迭代循环：跟"她"聊 → 记录人设崩掉的场景 → 针对这些场景补数据 → 再训一轮。每次迭代的数据集才是真正的资产，为后面的模型训练垫基。

## 角色音声模型+AEC 回声消除+VAD+声纹校验+活检(活体检测)+ASR+TTS合成

![语音交互流程图](/img/posts/glowspire-audio-flow.png)

**效果:**  复刻角色独有音色,会断句,有情绪语气语调,能识别个人音色
	1. 能复刻你想要的角色声色
	2. 说话有情绪,更贴近真人,说话更生动
	3. 只对你说话有响应,只认你的声音,是你的个人专属盆友哦

**云端或本地部署,输出情绪,有语气,tts接口选择**

- 音色克隆: minimax克隆id/本地训练音色模型
- 声纹校验: 现技术较成熟,使用CAM++可简单精准的实现
- 情绪输出: 把情绪标注能力"蒸馏"进微调模型/二次调用分析情绪关键词
- tts接口: minimax的tts接口(付费)/本地tts模型(GPT-SoVITS完全免费)

**注意事项:**
1. 本地tts模型免费但是效果差,且比较占性能,minimax付费但较便宜,效果更好
2. 隐私问题,因为一旦调用tts接口,消息暴露,对于该项目存在问题,不介意的话推荐选付费

### **第一步: 音色克隆**

推荐选择[MiniMax的官方克隆](https://www.minimax.io/audio)，需要谷歌账户登录，且首次克隆需要花费额度，只能充值，上传10秒以上的人声(越纯净越好)，直接克隆生成就行，会获取克隆模型的id，后续直接在接口中填写该克隆音色id即可，或者走 **GPT-SoVITS** 的微调流程产出 .ckpt 权重文件.
这一步的关键就在素材的质量,直接决定了成品效果。

### **第二步: 音频采集**

这一步就是把麦克风收到的声音变成程序能用的数字数据(PCM)。Electron 是 Chromium 内核，用 `getUserMedia` 打开麦克风拿到音频流，再接到 Web Audio 上:`AudioContext` + `AudioWorkletNode`，由 AudioWorklet 在**音频线程**上把声音切成 **512 个样本一帧**，逐帧抛回主线程。
采样率统一按 **16 kHz** 走，因为本地 whisper 只接受 16 kHz。麦克风自己是按原生率交付的(我的御葵 D80 是 USB 动圈麦，通常 48 kHz)，所以中间靠 `new AudioContext({ sampleRate: 16000 })` 让 Chromium 内部做一次重采样 —— 不是设备本来就这么给。
没用 `MediaRecorder` 而是用 AudioWorklet:
1. 它在音频线程上跑，主线程卡顿也不丢帧；
2. 是**一次开麦能供多方复用** —— 电平表/频谱、送识别的音频帧、声纹录入的录音都取同一路流，避免反复开麦(会触发授权弹窗和设备独占)。

采到的帧在主线程按 512 样本拼成整段，打包成 16 kHz WAV，`POST /asr` 交给本地 whisper。
这一步的关键就在**采样率**:率不对，whisper 直接识别不出来。

### **第三步: AEC回声消除**

AEC回声清除，这个的功能就是为了**把设备自己放的歌/说的话，从麦克风里消掉**
我的回声主要来源就是自己的TTS从扬声器播出来的声音。Electron 是 Chromium 内核，`getUserMedia({ audio: { echoCancellation: true, noiseSuppression: true, autoGainControl: true } })` 直接启用 WebRTC 的 AEC，只要采集和播放发生在同一个 Electron 窗口里（我的情况正好满足），回声抑制效果就不错。

### **第四步：VAD断句(Silero VAD)**

VAD 是"她怎么知道你说完了"这个问题的答案,2026 年本地项目的标配是 silero-vad ,一个 1.7MB 的 ONNX 模型,纯 CPU 跑,自带 Python 库,对音频流逐帧输出"有没有人说话"的概率,逻辑是：检测到语音开始 → 持续累积音频 → 连续 500-800 毫秒静音判定为你这句话说完了 → 把这一整段音频切出来交给下一级,这 500-800ms 是"尾静音",定短了容易截断你的话,定长了显得她反应慢.还有一个进阶功能叫打断(barge-in): 她在说话时,如果你开口了,VAD 立刻检测到,就中止 TTS 播放切回聆听状态.

### **第五步：声纹校验(CAM++)**

CAM++ 模型(ModelScope 上有现成的,中文场景 SOTA)在 CPU 上处理 3 秒音频只要十几毫秒.流程是: 注册阶段录你 10-30 秒的话,提取出一个 192 维的声纹向量存到本地文件.运行时把 VAD 切出的同一段音频也提一个向量,算余弦相似度,超过阈值(CAM++ 一般取 0.7 左右)判定是你本人.注意它和 ASR 是两码事：ASR 识别"说的什么",声纹只回答"是不是你",把校验放在 ASR 之前,不是你的声音就直接丢弃,省一次 ASR 计算.

**可选项: 活检**
防止别人放录音冒充你
但是在这个项目里实用性不大,因为这个也并非是啥隐私应用,只是这里做了声纹检验之后可以加入活检在你的声音上加一层锁,相关应用有微信的声音识别登录,和常规的声音开锁
- 实用路线(推荐)：随机口令挑战——每次解锁时让萤语随机报 4-6 位数字让你跟读，ASR 验证内容 + 声纹验证身份，"内容对 + 声音对"双因子。实现简单，对抗普通录音重放够用。
- 学术路线：AASIST 之类的反欺骗模型，ONNX 也有，但误拒率调起来麻烦.

### **第六步：ASR 语音转文字（SenseVoice）**

本地路线首选 **whisper.cpp**：和 llama.cpp 同门，二进制往 `portable/` 里一扔，backend 子进程调用，和 `llama.js` 管理 llama-server 的代码模式一模一样，ggml-small 模型约 500MB，中文效果可用。

### **第七步：LLM 生成**

把 ASR 的文本或者输入对话文本接到人设卡 system prompt 的完整对话历史里,然后模型输出结构化格式,比如 {"emotion": "温柔", "reply": "怎么啦，过来跟我说说"},解析出两个字段,文本送 TTS,情绪映射成 TTS 参数.
这里我额外做了一层过滤层
1. 过滤动作标签,即去除动作标签后发送给TTS,不播放动作内容
2. 过滤情绪标签和插入的语气词,发给用户看

### **第八步：TTS 合成与播放**

现在用 MiniMax API：拿 voice_id + 文本 + emotion 参数请求合成(可以开 SSE 流式，边合成边播),返回音频流交给 pyaudio 播放,以后切本地方案时,GPT-SoVITS 自带 API 服务模式,代码层只改请求地址,胶水层逻辑一模一样,CosyVoice 2 的流式合成对延迟更友好，作为本地方案的升级选项.
