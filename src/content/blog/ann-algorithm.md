ANN(Approximate Nearest Neighbor,近似最近邻)是向量数据库的核心引擎.先说要解决的具体问题,再讲它怎么做到的.

# 一、问题的真实成本

假设你有1000w条向量,每个向量1024维,然后给一个查询,要查找最像的10条.
基础的暴力做法叫 **Flat/暴力扫描:** 把 query 和 100 万条逐个算一遍距离,取最小的10个.
我问了一下ai,想看看具体差距有多大,但是....
算一下,`100w x 1024 = 10.24亿次乘加`,大约20亿次浮点运算.现代CPU单核 SIMD 大约 10~30 GFLOP/s,所以单次查询是 70~200毫秒,而且多核并行能压缩到几十毫秒.
就这?看着挺快啊,但是如果数据很大,达到 1 亿条,单次就是几秒,就彻底用不了了.

`tip: `这里的数据可是分块之后的,加上维度的话其实很大.

# 二、"近似"到底放弃了什么

ANN 的近似是用准确率换来了很快的速度.
这里有个必须搞准的指标叫**recall@k(召回率):** 真正最近的10条里,ANN 找回了几条?例如`0.95`就意味着平均会漏掉半条.

# 三、四种方法

| 方法       | 代表                  | 原理              | 现状                                 |
| -------- | ------------------- | --------------- | ---------------------------------- |
| 树 / 空间划分 | KD-tree , Ball tree | 递归切分空间,剪掉不可能的区域 | 低维有效,高维失效,向量检索基本不用                 |
| 哈希       | LSH ,随机投影           | 让相似向量落到同一个桶     | 理论漂亮,实际召回差,很少用                     |
| 聚类 / 倒排  | IVF , IVF-PQ        | 先聚类,只搜最近的几个桶    | 亿级场景常用,配量化                         |
| 图        | HNSW、DiskANN        | 建近邻图,在图上贪心游走    | **当前主流**,Qdrant/Milvus/Weaviate 默认 |
这里树为什么会在高维失效?就是这个**维度灾难:** 在 1024 维空间里,任意两点的距离会趋近于集中(即最远和最近差不多),所以"最近"这个概念就变得模糊了,同时你无法保证 **"我剪掉的区域里,没有答案"** ,这个承诺要求存在一个足够紧的下界,而在高维中不存在这样的下界,所以树的**失败是必然的**,不是工程能优化就解决的问题.

所以只剩下"图"和"聚类"这两条路了.

# 四、HNSW: 主流方案(图)

HNSW 全称`Hierarchical Navigable Small World`.名字很长,但拆开只有两个想法.

## 一、把点连成一张近邻图

首先,查询进入的点不是随机的,而是固定的,我们称为 **Entry Point(EP)** ,要查找到的称为 **query**,在这一层当中我们要找到从开始到结尾的这段的最短路径.
**贪心算法实现:** 给每个向量记下离他最近的几十个向量是谁,找近邻的时候只找离目标更近的邻居,这样每步都在往"看起来更近的方向"走.

但是如果只有这个近邻表的话,光靠贪心走,很容易出现问题.

1. 死胡同: 当走到一个点的时候,近邻全是更远的点,自己只差一点点就走过去了,不动了
2. 慢!: 长距离跳转依然很慢,容易在局部区域绕路.
上述问题本质就是所有的连接都很短,只连接近邻,没有直达的大路

所以要建一条大路,使得"武汉"和"北京"连通,而不是一个一个城市的移动,遇到地形还要绕路.
但是在一张图上建立这个"大路"很丑,所以引出多层图的方法.

## 二、分层图

从底层选一些点进行连接,作为新层,再上面作同样操作.
同样也是选取随机的点进行连接,只不过分为很多层,我拿三层作为说明.

- 顶层: 只有几个点,彼此的距离很远,用来跨越较远的距离.
- 中层: 用来逐渐缩小查找的范围.
- 底层: 全部的点,作为精细查找. 

你看,像不像时针,分针,秒针,想要调到某个时间的时候,先动时针再动分钟,最后用秒针微调.
而**同一个点在不同层里的位置是一样的**(只是上层不一定有它),所以你可以从上层“垂直降下来”到下一层的同一个位置.HNSW 的结构看起来就是一个跳表(skip list).

## 核心参数: 

**四大衡量:** Recall , Latency , Build Cost , Memory.

1. **M(图连接密度):** 该值越大-> Recall越大, Memory越大, Build Cost越大.
2. **efConstruction(建图搜索宽度):** 该值越大-> 图质量越好, Build Time越大, CPU 越高.
3. **edSearch(查询搜索宽度):** 该值越大-> Recall越大, Latency 越大, CPU 越高.

M = 修多少路,efConstruction = 修路时找多认真,efSearch = 导航时找多认真
唯一在线上能调的就是efSearch,越大越准越慢.

## 为什么近似?

因为贪心搜索仍然可能走错: 上面的例子恰好走对了,但换个数据分布可能停在次近的那个点上.所以它只承诺“大概率找到最近的”,不承诺“一定”.

# 五、IVF + 量化(聚类)

这是两个独立的部分,**IVF**解决要比多少次,**量化**是解决每条占内存过大.

## 一、IVF(倒排文件索引)

这个就是一种`候选集缩小策略`,就是当我们要查 100w 条向量,太慢,于是我们想到分成 1000 组,然后到最可能的那几组里面找.

### **K-means分组:**

1. 随机挑 k 个点当"组长",即分为 k 个簇(nlist).
2. 每个点都和靠近自己的"组长"组合.
3. 为了防止"组长"出现边缘情况,我们每组重新选组长,把组内平均位置拿来当新组长.
4. 重复平均选,直到"组长"不变.

### **分组完成后,查询流程如下:**

1. 计算 query 到 1000 个“组长”的距离,只需 1000 次计算,很快.
2. 选出最近的 `nprobe` 个组,例如 2 个.
3. 只在这 2 组内逐个比较,此时只需比较 2000 条,而不是 100 万条.
4. 合并候选结果,得到Top-k.

这里其实可以看出来,如果`nprobe`过大,则退化成暴力扫描,如果过小,则很容易漏掉答案(就在隔壁呢,就差一点点).
分组按空间距离划分,因此“离 query 近的点”大概率落在“离 query 近的组”里,多数情况下成立,但边界附近会出错,这就是“近似”算法的代价.

## 二、量化

IVF 只减少了**比较次数**,一条向量仍占用 4096 字节.1 亿条 × 4096 字节 = **409 GB**.内存装不下.
同时用**flat**暴力进行查询同样很慢.
所以 IVF 只解决了找,没有解决优化内存大小的问题,后面我们就要考虑向量怎么存,怎么算.

### **一、SQ8(标量量化)**

本质就是**降低向量数位的宽度**,就是降低精度,把 float32 将为 int8 
对一个维度来说,把这个区间等分为 256 档,然后把每个数值取整到最近的那一档,只记档位编号(0~255),不记原数值.
具体来说就是编码和解码两个操作,这里给出公式: 

- **编码:** code = round( (x − min) / (max − min) × 255 ).
- **解码:** x = code / 255 × (max − min) + min.

 **为什么"几乎无损",误差到底多少?**

关键结论: **每一维的最大误差 = 档距的一半 = `(max − min) / 510`.​

以 1024 维,每维区间宽度约 2 为例: 

- 档距 = `2 / 255 ≈ 0.0078`
- 单维最大误差 ≈ `0.0039`
- 1024 维累积，误差按平方和叠加：`√(1024 × 0.0078² / 12) ≈ 0.072`

而 1024 维向量之间的典型距离量级是 **13** 左右.

**0.072 / 13 ≈ 0.5%.** 也就是说,量化把距离扰动了几百分之一,远小于真实近邻之间的差距.所以排序基本不变,召回几乎不掉.
这也解释了为什么 SQ8 是 8 bit,而不是 4 bit.8 bit 的误差已经落在"远小于信号"的区间里,再往下压就开始伤到排序了.

如果你看懂了上述的方法,那么可能会想到一个问题,这个映射的范围取决于最大和最小,但是如果极值的数量与平均大小的数相差太大,比如某个维度 99.9% 的值都在`[0,1]`,但有一条向量出现了`50`:

- 区间变成`[0, 50]`,档距变成`0.196`.
- `[0, 1]`这段只占 **5 档**.
- 精度从 256 档掉到 5 档,这一维基本废了.

解法不是去删除离群值,而是**不要取真实 min/max,改取分位数**: 比如取 1% 和 99% 分位作为区间端点,超出的直接截断到端点.这样极值会失真,但它本来就只有极少几条,总体精度反而大幅提升.

### **二、PQ(乘积量化)**

这个量化的做法和之前的 IVF 很像,这次是把一条 1024 维的向量切成 64 段,每段 16 个数字.
然后**对每一段单独做一次 k-means,聚成 256 类**.这一步和前面讲的分组完全一样,只是作用在 16 维的小空间里,而不是 1024 维的大空间.

### 三、为什么压 64 倍还能用

**64 个字节,每个字节有 256 种取值,能组合出的数量是 256⁶⁴ = 2⁵¹² ≈ 10¹⁵⁴.**

而我们要存的只有 10⁸ 条向量.

**表达能力比需求高 10¹⁴⁶ 倍.** 因此从数学上看,这 64 个字节几乎没有理由无法区分这 1 亿条向量.

对比一开始那种“整条向量聚 256 类”的做法: 表达能力只有 **256**.却要区分 1 亿条——这才是真正的灾难.

**切段的意义就在这里**: 把“每段只有 256 种可能”这个限制,分散到 64 个互相独立的段上,组合起来就得到天文数字.这跟调色板的道理一样: 一种颜色对应一个调色板取不出细腻的图,但 64 个调色板各管一块区域,就能拼出接近原图的效果.

这也是它叫「**乘积**量化」的原因——**它的表达能力来自 64 个集合的乘积,各段可能性的乘积构成总表达力**.
### 四、压完之后怎么算距离

关键: **不解压,解压回 4096 字节就白压了.**

做法是**查表:**

1. 把 query 也切成 64 段.
2. 预先算好「query 的每一段,到该段 256 个候选中心的距离」→ 64 × 256 = **16384 个数字**,做成一张表(一次算完，所有候选共用).
3. 现在给一条压缩向量(64 个字节),它的距离就是: **按这 64 个字节去表里查 64 次,然后加起来**.

对比一下：

- 原始: 一条候选要算 **1024 次乘加**
- 压缩后: 一条候选只要 **64 次查表相加**

**又快又省.​这就是为什么量化能同时降低内存和延迟.**

# 六、没有十全十美的方法

## 对于 IVF :

1. IVF通常需要训练,不是零成本建索引
2. 数据分布不均时,簇大小可能失衡
3. 数据变化很大时,可能需要重训
4. 数据分布不均时,VF-Flat/IVF-PQ的区别,主要体现在簇内如何存储.

## 对于量化: 

从 Flat 到 SQ 再到 PQ ,内存占用越来越低,速度越来越快,同时 recall越来越低.

这就是"近似"换来的结果,我们没办法做到十全十美,也不要无脑选择技术含量最高的,最新的,我们要根据实际业务需求来进行自定义搭配,**没有更优,只有更好的选择**.
