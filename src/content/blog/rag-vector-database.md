RAG 和向量数据库这套东西,很多人认为就是塞一个数据库,然后模型到里面去搜素答案.实际上它是一整条工程链路,我会按照`为什么需要RAG`,`什么是RAG`,`具体怎么做`,`向量数据库到底是什么`,`向量检索链路`,`现在的embedding模型`,以及一些`进阶做法`和`个人的实践经历`来讲.

# 一、为什么需要RAG

大语言模型有三个绕不开的硬伤: **知识有截止时间**(训练完就冻结了,除非联网搜索),**不知道就编**(幻觉,而且非常自信,很容易让你盲目相信),**没见过的内容**(你的私有数据,公司的信息,你的代码书写习惯).

对于上述问题,现在行业里的解决方法是: 

- 微调把知识烧进权重,贵,更新慢,微调有损失,照样幻觉;
- 超长上下文把整库塞进prompt,成本高且中间段落容易被忽略;
- RAG——先把相关资料检索出来,再让模型"根据以下材料回答";

就像我们开卷考试一样,能拿出一本整理好的带目录的课本,对于用户来说,模型不是变聪明了,而是**答案有据可查,能给出引用,且能随时更新**.

![RAG 索引与在线检索流程图](/img/posts/rag-pipeline.png)

上图里有两条独立链路: 上面只在内容更新的时候跑,下面每次询问都要跑.很多人调不好RAG,问题都出在上面那条路中,在索引期偷懒,检索期再怎么调都是徒劳.

# 二、RAG怎么做的

## 第一步: 文本怎么变向量

**主要分四步(embedding模型做的):**

1. **分词(tokenize):** 把文本切成模型认识的 token,token 不等于字,也不等于词,模型只认识词表里有限的那些 token，所以必须先切。
2. **逐层计算:** 每个 token 先有一个初始向量,然后经过几十层网络,每一层都会"看一眼"周围的 token(这就是 attention),把自己调整得更贴合当前语境,所以"苹果"在「吃了一个苹果」和「苹果发布了新手机」里,最终得到的向量是不同的——它区分的是语境中的意思,不是这个词本身.
3. **池化(pooling):** 一段话有5个 token 就有5个向量,但我们只要一个,做法是取一个特殊位置或把它们平均起来。
4. **输出:** 一个定长向量,通常再做一次归一化(把长度变成1),这样后面算余弦最省事.

Embedding 模型把任意长度的文本压缩成一个**定长的稠密向量**.关键在于他编码的是**语义**而不是字面: 

- "我想退钱" 和 "如何申请退款",字面几乎零重叠,但向量余弦相似度能到 0.85 以上;
- 反过来 "苹果手机保修" 和 "苹果价格行情",字面高度相似,向量却会拉开距离;

这就是为什么向量检索能解决传统关键词搜索的死穴——用户是不会用你文档里的原词提问的.

## 第二步: 怎么对应向量的

离线编码的是"文档块",在线编码的是"问题".两者被映射到同一个空间,所以才能直接比距离——这是 embedding 模型最了不起的地方,它让"问题"和"答案段落"变得可比.

衡量"距离"的方法有三种,选错了不会报错,但是会掉召回率: 

- **余弦相似度** $cos(a,b) = \frac{a · b}{|a| · |b|}$ —— 只看方向不看长度,最常用,适合文本;
- **内积(dot product)** ​—— 向量预先归一化后和余弦完全等价,但少一次除法,所以索引内部通常用内积;
- **欧氏距离(L2)** —— 关注绝对位置,图像,推荐场景更多见.

这里要注意,不同的 embedding 模型训练时用的度量不一样,离线检索和在线询问检索都必须使用同一种,混用会明显掉效果.

## 这里有个问题 分块越多越好吗?

因为噪声会干扰判断.塞进去 20 块,其中 17 块不相关,模型反而容易被带偏,而且成本线性上涨.**宁精勿滥**——这是 RAG 调优里最反直觉,也最常被违反的一条.

# 三、什么是向量数据库

我们还是来看看,这个向量库要解决什么: 

- **元数据过滤**(带 filter 的 ANN 是公认难点,通常是"先按条件缩小子集再搜"或"搜完再过滤"的权衡)
- **增删改**(HNSW 删除实质是软删除 + 定期重建)
- **持久化与副本分片,多租户隔离**.

所以可以看出,它并不是一个简单的索引库,而是一个数据库.

选型上的常见组合: Milvus / Qdrant / Weaviate / Pinecone 是专用向量库;**pgvector** 适合已有 Postgres 且数据量在千万级以下的场景;Chroma、LanceDB 偏轻量本地.注意 **FAISS 是算法库不是数据库**——没有持久化,没有元数据,没有并发.

如果片段量很大,原始数据就很大,如果每次都全量算一遍距离,那么每次查询的速度极慢,对应线上根本没办法用.

所以向量库的核心就是 **[ANN(近似最近邻)](/post/ann-algorithm):** 不做精确的搜索,而是用索引结构把搜索范围砍掉几个数量级,牺牲`1%~5%`召回率的同时时换取`100~1000`倍的速度.三条主流路线如下: 

| 索引               | 核心思路          | 优势           | 代价             |
| ---------------- | ------------- | ------------ | -------------- |
| **HNSW**         | 分层图，从稀疏顶层贪心下降 | 召回率高、延迟低、免训练 | 内存占用大、构建慢、删除麻烦 |
| **IVF / IVF-PQ** | 先聚类分桶，只搜最近几个桶 | 内存小、易扩展到亿级   | 需要训练、召回略低、调参敏感 |
| **Flat（暴力）**​    | 全量精确扫描        | 100% 准确，可做基准 | 慢，仅适合小规模或评测基线  |

详细的内容在[ANN算法讲解](/post/ann-algorithm),感兴趣的可以看看;

# 四、检索链路

之前讲了怎么切词成向量的,向量怎么进行存储的,现在才到最关键的"向量检索".工业级检索其实是一条混合流水线,因为**单靠向量一定会有盲区:** 型号,人名,错误码,缩写这类精确词面,向量模型经常识别不准——搜 "ERR_5021" 可能返回一堆语义相近但码完全不同的文档.

所以标准做法就是向量 + 关键词双路召回,再融合,重排.

有些人会在`embedding`模型中看到`嵌入`或者`重排序`的标签,我来说明是什么意思.

- 嵌入: 把一段文本**单独**编码成一个向量,query 和文档各编各的,然后比距离.
- 重排: 把 query 和文档**拼在一起**送进模型,直接输出一个相关性分数.

**融合用 RRF 最省事**.两路检索的分数体系完全不同(余弦相似度是 0~1,BM25 是任意正数),没法直接相加.RRF 干脆只看排名:`score = Σ 1/(60 + rank)`,把每个文档在两路里的名次倒数相加.免调参,效果稳,比强行归一化加权靠谱得多.

**重排的价值被严重低估**.向量检索用的是双塔结构——query 和文档各自独立编码再比距离,快但粗糙.Cross-encoder 把 (query, chunk) 拼在一起过一遍模型,让两者在注意力层里充分交互，准确率高一个档次，代价是慢几十倍.所以标准做法是**粗排召回 30~100 条,重排只算这几十条**,取 final top-5 进上下文.

我认为最重要的环节: 切分(chunking)​ 512~1024 token 一块,10%~20% 重叠是常见起点,但真正有效的做法是按文档自身结构切——按标题层级,按段落,表格单独处理并保留表头.切碎了丢上下文,切大了混入无关信息,这才是 RAG 收益最高的一个环节.
