现在这套 RAG 可以概括为：**本地整理博客、生成向量，再由线上后端做混合检索、重排和回答生成。向量存放在 Neon PostgreSQL 的 pgvector 字段中。**

### 1. 博客内容怎样变成知识库

构建时，程序通过 Astro Content Collections 读取文章，提取：

- 文章 ID、标题、网址、语言；
- 标签和分类；
- Markdown 正文。

草稿、密码文章、包含加密块的文章会被排除。正文快照保存在本机，不会随网站公开发布。公开的只有版本指纹和文章数量。

随后使用 Markdown AST 切分文章，主要依据是**标题层级、段落和代码块**。片段会带上所属文章与章节，例如：

```
文章：铃月助手设计
章节：知识库 / 混合检索
正文：……
```

这样，“混合检索”这一小段即使单独被召回，也保留了基本背景。

当前切分有两个具体特点：

- 每个片段最多 512 个 BGE-M3 tokens，包含文章标题、章节路径和正文；优先保留段落、句子、列表项和表格行，相邻文字最多重复 48 tokens 的完整末句。
- 代码能放下时整块保留，超长代码优先沿已有换行分段。单行确实超限时才拆分，并标明续段；每段围栏闭合，不在原始代码内部人为添加换行，也不保证分段代码能独立运行。

**现在使用真实 tokenizer：离线切分采用 BGE-M3 的固定词表，聊天文本预算采用当前 DeepSeek 模型的固定词表，并单独预留消息封装空间。实际消耗与计费以 API 返回的 usage 为准。**  

### 2. Embedding API 负责什么，我们自己实现什么

片段编码使用硅基流动提供的 **`BAAI/bge-m3`**，向量长度固定为 1024。提问时，也使用同一个模型编码问题，保证问题和文章处于同一向量空间。

当前只用了 BGE-M3 的 **dense embedding**。模型虽然还支持稀疏检索、多向量检索，但本项目没有接入那些输出。

我们自己实现的是：

> 内容筛选 → 切分 → 元数据与哈希 → 增量编码 → 数据发布 → 检索融合 → 重排 → 上下文组装 → 引用返回。

API 提供模型推理，整条 RAG 流程由项目里的 TypeScript 代码控制。

生成时还会查本地向量缓存：

```
缓存键 = SHA256（Embedding 模型名 + 片段内容哈希）
```

未变化的片段直接复用，只有新增或变化的片段才调用 Embedding。**重新遍历文章，不等于重新付费编码全部文章。**

### 3. 向量数据库里实际存了什么

现在让 PostgreSQL 同时保存正文、向量和版本信息：

| 数据表          | 作用                           |
| ------------ | ---------------------------- |
| `chunks`     | 片段正文、文章信息、关键词、`vector(1024)` |
| `versions`   | 每批知识数据的版本和数量                 |
| `control`    | 当前有效知识版本和发布序号 |
| `withdrawals` | 独立撤回名单，排除已删除或转私密文章 |
| `embeddings` | 已发布的向量缓存                     |

`chunks` 的核心结构可以理解为：

```
知识版本 + 片段ID + 文章ID + 正文/元数据 + 1024维向量
```

向量查询实际使用：

```
SELECT id
FROM lingyue.chunks AS c
WHERE version = 当前版本
  AND NOT EXISTS (
    SELECT 1 FROM lingyue.withdrawals AS w
    WHERE w.document_id = c.document_id
  )
ORDER BY embedding <=> 问题向量
LIMIT 40;
```

`<=>` 表示余弦距离，距离越小越接近。

**当前采用精确搜索，没有建立 HNSW 或 IVF-Flat 近似向量索引。** 我的博客目前还是小规模数据，直接计算距离更简单，速度也在线，也避免了近似搜索和过滤组合带来的漏召回。精确排序本身不保证语义理解正确，结果仍取决于切分与模型表达。

### 4. 用户提问后，RAG 怎样运行

![铃月 RAG 问答链路：双路召回、融合精排与带来源的回答](/img/posts/belluna-rag-retrieval.svg)

提问先补齐文章范围和对话上下文，再做语义、关键词双路召回：语义分支最多取 40 条，关键词分支最多取 20 条，RRF 合并后保留 20 个重排候选。BGE 重排与证据筛选后，最多 6 段、3,500 tokens 的资料交给 Flash 生成带引用的回答。点击流程图可以放大查看。

这里有几个要点注意一下: 

当前**PostgreSQL**版本使用中文分词、英文标识符和汉字二元词，再按标题 4、标签 2、正文 1 加权匹配。

它不是 BM25，没有 BM25 的词频和文档长度校正，也不是 BGE-M3 的稀疏向量检索。这是迁移中的一处算法变化。

**两路结果用 RRF 融合。** 它根据各自排名累计分数，避免直接相加“余弦距离”和“关键词分数”这两种不同量纲的数值。

**融合之后有重排。** 调用硅基流动的 `BAAI/bge-reranker-v2-m3`，让重排模型重新判断“问题—候选片段”的相关程度。程序保留 relevance_score，过滤绝对分数低于 0.1 或低于本次最高分 15% 的候选，并去除近重复；全库问答每篇最多 3 段，总计最多 6 段、3,500 个聊天文本 tokens。资料不足时可以返回空证据，不为凑数补噪声。相关性分数不等于答案正确概率。

所以一次普通知识问答，在没有缓存时，通常包含三类模型调用：**问题 Embedding、候选重排、最终对话生成**。

### 5. 它怎样结合当前文章、历史和引用

当前实现有轻量的上下文处理：

- 问“这篇文章……”时，会限定在当前文章中检索。
- 问“它、刚才那个……”时，会把上一条用户问题补入检索查询。
- 总结当前文章时，会额外选取不同章节的代表片段，增加覆盖面。
- “在吗、晚安”等明确的简短闲聊会跳过检索。

这属于规则式上下文补全，**目前没有实现 HyDE 或大模型多路查询改写**。

选出的资料被编号为 `[S1]`、`[S2]`，和铃月人设、有限历史一起交给聊天模型。前端收到来源标题、章节和链接，再显示“已引用／相关资料”。

程序目前检查的是回答中出现了哪些引用编号，**没有自动验证每句话是否确实被该来源支持**。

### 6. 更新与删除

当前采用的是**完整版本发布、增量计算向量、独立撤回保护**：

1. 本地构建新的公开文章快照。
2. 明确开始发布时，将旧有效版本中不再公开的文章加入独立撤回名单，并取得发布序号。
3. 复用未变化的向量，只为新增或变化的片段生成向量。
4. 将完整新版本写入 Neon，暂不启用。
5. 推送 GitHub，等待 Vercel 部署，核对网站知识指纹。
6. 同时校验发布序号和旧有效版本，在数据库事务中切换 active_version。只有这时才恢复本次完整公开版本中的撤回文章。

本地编辑、构建和单独运行 generate:knowledge 都不会实时改变云端；publish:blog 或 knowledge:begin 才是明确的线上发布动作。

向量、关键词与正文读取都在取候选前排除撤回文章，重排后、模型调用前和返回来源时还会复核。因此后续向量生成、上传或部署失败，也不会重新召回已撤回内容；其他文章继续使用旧有效版本。

另一次发布或人工撤回会使旧发布凭据失效，旧任务不能把文章重新放回来。紧急撤回可单独运行 knowledge:withdraw --id=文章ID；恢复公开则需要重新发布并验证启用。

旧版本保留 7 天供清理和故障处理，逻辑撤回不等于立即物理擦除。已经发送给模型的请求、访客收到的文字和浏览器旧历史无法追回。

### 7. 如何检查效果

目前建立了 60 组问题、标准答案与原文证据的回归集，开发集 36 组、留出集 24 组。对关键词召回、融合、重排和最终证据分别计算事实级 Recall、MRR 与片段级 nDCG，并检查无答案问题是否仍被塞入资料。

这些标签由助手依据原文整理，仍待人工复核；正例集中于六篇技术和设计文章。小数据、高分不代表已经覆盖真实访客问题，也不代表最终回答准确率达到 100%。
