# 铃月 RAG 实现与本轮优化

本轮代码以 Vercel + Neon/PostgreSQL/pgvector 为目标，保留精确余弦检索。
优化前快照为 127 篇、510 片段；新切分在同一批文章上得到 569 片段。
这些数字是当前本地快照统计，不是可支撑规模的上限。

## 字节、token 与两套预算

UTF-8 字节是存储编码大小，token 是模型词表对文本分词的结果，没有固定换算比。
“铃月的向量检索使用 PostgreSQL 和 BGE-M3。”是 52 字节，当前固定词表下
BGE-M3 是 22 tokens（含特殊标记），DeepSeek 是 13 tokens（纯文本）。
旧代码把字节当预算代理，通常偏保守，也无法准确对齐 embedding 和聊天模型的限制。

- 离线切分：BGE-M3 tokenizer，512 tokens **包含文章标题、章节路径和正文**。
- 聊天证据：DeepSeek tokenizer，最多 3,500 文本 tokens、最多 6 个片段。
- 完整输入：人格、证据、历史、用户问题一起计数，另留 256 + 每消息 16 tokens 的封装余量。
  超预算先移除较早历史，仍超出则移除排名较后的证据，不切断代码块。
- 本地能准确计数的是固定词表的文本，不是服务商内部封装、隐藏系统消息或模型别名变动。
  **计费和实际消耗以 API 返回的 usage 为准**。更换聊天 checkpoint 时需重新核对 tokenizer。

`knowledge:tokenizers` 从官方模型仓库固定 revision 下载词表和配置，并检查内容摘要。
版本/摘要在 `src/server/lingyue/tokenizer-manifest.ts`。只下载词表，不下载模型权重。
本机缓存被 Git 忽略；Vercel 仅打包聊天词表到函数私有目录，不向浏览器发送词表、正文快照或向量。
首次干净构建需要访问 Hugging Face；失败时终止构建，不偷偷退回字节计数。
已有本机代理仅用于公开词表下载，不改变模型 Key 的传输路径。

## 文章怎么切

`scripts/lingyue/markdown.ts` 使用 remark AST，不执行 HTML、脚本或 MDX。

1. 按章节边界分组，每个片段保留完整章节路径。
2. 尽量保留段落、列表项和表格行；超长内容优先在句子/自然换行处切分。
3. 相邻文字最多重复一小段完整末句，限制在 48 BGE tokens；不把任意尾字符当重叠。
4. 代码能放下就完整保留；放不下优先沿已有换行分段。单行确实超限时才拆字符，
   不在原始内容内部人为插入换行，并标明“代码分段，需结合原文上下文”。每段 fence 独立闭合。
5. 表格分段尽量重复表头；极长单行退化时明确标记分段，不能伪称完整表格。
6. 记录 token 数、内容类型、原文范围和续段标记。相同内容片段的 ID 不再依赖全篇序号，
   在前面插入独立章节不必改变后面的片段 ID。

512 是可调整的工程参数，当前由结构与评测验证，不是 BGE 的最大输入长度。
切分变化会形成新 pipeline 指纹，本次需要一次新的 embedding 生成；以后未变化片段复用缓存。
缓存键仍包含模型名和片段内容哈希。生成命令只写本机缓存，不改变线上知识版本。

## 检索与证据筛选

请求 → 指代补全 → 两路召回 → RRF → BGE 重排 → 证据筛选 → 模型流式回复。

| 步骤 | 当前实现 |
| --- | --- |
| 语义召回 | SiliconFlow BAAI/bge-m3，1024 维；pgvector 精确余弦 top-40 |
| 关键词召回 | 中文词、标识符、汉字二元词；标题/标签/正文权重 4/2/1，top-20；并非 BM25 |
| 融合 | 应用端 RRF，保留最多 20 个重排候选 |
| 重排 | SiliconFlow BAAI/bge-reranker-v2-m3，保留排序与 relevance_score |
| 证据 | 分数至少 0.1，且至少为本次最高分的 15%；近重复去除；全库问答每篇最多 3 段 |
| 预算 | 最多 6 段且不超过 3,500 聊天文本 tokens；可以少于 6 段或为空 |

这里候选 top-k 和最终证据数量是两个参数，不会为了凑满 6 段把弱相关内容都塞给模型。
近重复使用同文四字符片段 Jaccard；相同哈希直接去重。它是轻量近重复检查，不能识别全部语义改写。
重排失败降级为少量混合召回，最多两段，标记降级；没有同等可信的分数时不伪造分数。
明确“总结这篇”的请求例外：在指定文章内抽取章节覆盖样本，不拿单段相关性门槛替代全文覆盖。

重排分数不是校准后的回答正确概率，也不能证明证据包含答案。
例如问“项目昨日收入”，检索到产品设计仍然只是话题相关；模型必须依据资料坦率说不知道。
目前没有 HyDE 或 LLM 多路查询改写，只有规则式指代/当前文章补全；这次没有为此增加一次模型调用。

小数据下精确扫描没有 ANN 的召回损失，也省去近似索引调参和维护。
将来只有在测得检索延迟/数据库成本成为瓶颈后，再比较 HNSW 的速度与召回折损；现在不建 ANN 索引。

## 更新与撤回

本地编辑、构建、生成向量与线上发布是不同操作。`publish:blog` 的时序是：

```text
构建新的公开快照
  → 开始发布：撤回旧有效版本中已经不在新公开快照的文章，取得发布序号
  → 生成缺失向量（只在本机缓存）
  → 事务上传完整、未启用的新版本
  → 推送 GitHub，等待 Vercel 站点指纹匹配
  → 核验发布序号和旧有效版本，事务切换有效版本
  → 恢复本次完整公开版本中的撤回文章，尝试清理退休版本
```

撤回名单不依赖新向量成功：后续生成、上传或部署失败，删除/私密文章仍被排除，其他文章继续用旧版本。
关键词、向量和正文读取都先过滤撤回名单；重排后、模型调用前和返回来源时再次检查。
新发布或人工撤回会增加 publication_seq，旧发布包括“启用同一版本”的重试也不能越过它恢复文章。
恢复公开必须完成一次新的验证启用；单纯上传、重排缓存和查询向量缓存都不能取消撤回。

`knowledge:withdraw --id=文章ID` 可独立紧急撤回；它不会删除 Markdown 文件。
旧版本和已撤回向量保留到后续清理，逻辑上不可检索不等于即时物理删除。
已发给模型的请求、访客已收到的文字和浏览器旧历史无法追回；这套机制不是追溯擦除机制。
修改但仍公开的文章在完整新版本启用时切换，不会让旧、新片段混在同一有效版本里。

## 评测与边界

`evaluation/lingyue/cases.json`：60 组，dev 36 / holdout 24；50 个可回答问题与 10 个无答案问题。
包含标准答案、文章 ID、原文证据。正例集中于六篇技术/设计文章，是有针对性的回归集，
不是覆盖 127 篇的随机样本；标签由助手依据原文整理，**待作者人工复核**。

运行 `pnpm knowledge:evaluate --split=dev`；固定参数后再运行 `--split=holdout`。
用临时本机 PostgreSQL/pgvector 执行生产检索 SQL；只调用 embedding/reranker，不调用聊天模型，不连接 Neon。
模型响应缓存在被忽略的本机目录，相同请求可复用；网络降级会让评测失败，不能冒充完整链路结果。

- Recall@k 按标注事实组计数，必须命中正确文章且证据原句实际出现在片段标题、章节或正文中。
- MRR@k 使用首个证据命中的倒数名次。
- nDCG@k 对包含标注原句的片段作二元相关性判断，用整个当前切分语料计算理想排序。
  同一事实可能存在于相邻重叠片段，因此还需同时看事实级 Recall，不能只看 nDCG。
- 分别报告关键词@10、RRF@20、重排@6、最终证据@6，避免用召回成绩代表最终上下文。
- 无答案问题按完全无关/同话题缺事实分别记录“仍给证据”的比例；它不是模型幻觉率。

小语料、问题难度和标签覆盖都会影响高分。没有测答案事实一致性、引用是否逐条蕴含答案、
真实访客多轮输入和生产网络延迟，因此不能宣称端到端准确率 100%。
本轮前后对比见 [评测结果](../../evaluation/lingyue/RESULTS.md)。
